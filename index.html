Alle Einzelheiten als Tabelle

Eine Zeile je Schritt · Spalten = wer handelt · letzte Spalte = wann der Chat anhält. Hooks sind Skripte, die von selbst laufen; die Spalte Git zeigt, was in den Repos ankommt.

2Regeln und Prüfung

Jede Regel hat einen Hook, der sie automatisch prüft – zu einem festen Zeitpunkt. Wie tief eine Änderung geprüft wird, legt ihre Prüfstufe fest.

Regel (Soll)prüft automatisch (Ist)läuft
Vor der Arbeit das Lagebild: parallele Chats, Claims, offene Übergabensession_overview.pybeim Chat-Start
Nur passende Skills laden; ab ~100k Token neuer Chat mit Übergabechat_length_hint.pybei jeder Nachricht
Jede Datei wird vor dem Ändern zum Claim; fremde Claims nur nach Absprachetodo_claim_hook.pyvor jeder Dateiänderung
Kein breites pkill, kein git push --force, kein Umgehen von Schutzmechanismenpre_tool_guard.pyvor jedem Befehl
Jede gespeicherte Datei fehlerfrei: Syntax, UI-Regeln, Ecken ≤ 8 pxpost_edit_check.pynach jeder Dateiänderung
Nur geprüfte Stände committen: Tests, Begriffe, Formattools/pre-commitbei jedem Commit
Jede Antwort im festen Format: Ergebnis, Warnungen, Prüf-Tabelle, Statusformat_check.pyam Ende jeder Antwort
Offener Rest wird übergeben, der Claim gelöschtchat_handoff.pybei „chat weiter“ im neuen Chat
StufeÄnderungPrüfung vor „fertig“
0trivialText, Kommentar, Doku, Config ohne WirkungHooks + pre-commit
1kleinBestehendes Element, ein Bereich, ≤ 3 DateienSchnelle Prüfungen, UI hell + dunkel; Bugfix: Originalsymptom + 1 Test

So greifen die Teile ineinander

Regeln
RULES.md für alle Projekte + AGENTS.md je Projekt; jeder Chat liest sie zu Beginn, das Projekt ergänzt sie, Sicherheit hat immer Vorrang
Rollen
Organizer → Fachrolle → Prüfer → Synchronizer: der Chat wechselt die Rolle mit dem Schritt und nennt sie in der Antwort
Skills
Anleitungen je Thema; der Chat lädt nur die zur Aufgabe passenden, über die Finder-Tabelle in RULES.md
Agenten
Hilfs-Chats für Suche, Tests und Reviews; sie liefern nur das Ergebnis, der Haupt-Chat prüft es (git diff)
Hooks
Laufen bei Ereignissen (Tabelle oben), ohne dass jemand sie aufruft; Codex und Gemini bekommen sie über Bridge-Skripte
Memory · Claims
Beides liegt in Git: Memory hält Entscheidungen über Chats hinweg, Claims zeigen parallelen Chats, wer welche Datei bearbeitet

4Begriffe

Kurz erklärt – für alle, die zum ersten Mal hier sind.

Repo
Git-Ordner mit vollständigem Verlauf aller Änderungen; hier privat auf GitHub, außer wenn ausdrücklich öffentlich.
Nichts geht verloren: jeder Stand lässt sich zurückholen, alle Rechner arbeiten mit demselben.
Regeln
RULES.md für alle Projekte + AGENTS.md je Projekt: Vorgaben, die jeder Chat zu Beginn liest.
Jeder Chat arbeitet gleich – egal mit welchem Werkzeug, in welchem Projekt.
Chat
Eine Sitzung mit einem KI-Werkzeug (Claude Code, Codex, Gemini) für eine Aufgabe; mehrere laufen parallel, jeder mit eigener ID.
Aufgaben laufen getrennt und parallel, ohne sich gegenseitig zu stören.
Rolle
Tätigkeit des Chats in einem Schritt: Organizer, dann Designer, Entwickler oder Redakteur, dann Prüfer, dann Synchronizer.
Jeder Schritt bekommt den passenden Blickwinkel – vom Plan bis zum Commit.
Organizer
Rolle am Anfang: schätzt Aufwand, wählt Fachrolle und Prüfstufe, plant und stellt Rückfragen.
Die Aufgabe ist geklärt, bevor sich Dateien ändern.
Prüfer · Definition of Done
Der Prüfer kontrolliert die festgelegten Fertig-Kriterien in der passenden Prüfstufe und verlangt einen Beleg aus dem aktuellen Chat.
Nur nachweislich richtige Stände gelten als fertig.
Synchronizer
Abschlussrolle: committet und pusht den geprüften Stand, stimmt parallele Chats ab und übergibt offene Reste.
Repos und Arbeitsrechner bleiben auf demselben Stand.
Skill
Anleitung zu einem Thema (z. B. Vorschau, Commit, UI-Änderung); der Chat lädt sie nur, wenn die Aufgabe das Thema berührt.
Fachwissen nur bei Bedarf → kurzer Kontext, weniger Token.
Agent
Hilfs-Chat mit eigenem Auftrag – Suche, Tests, Review; liefert nur das Ergebnis zurück, der Haupt-Chat prüft es.
Lange Suchen und Logs bleiben aus dem Haupt-Chat; Prüfung mit frischem Blick.
Hook
Skript, das bei einem Ereignis automatisch läuft: Chat-Start, vor einem Befehl, nach dem Speichern, am Ende der Antwort.
Regeln greifen automatisch – auch wenn ein Chat sie vergisst.
Memory
Notizen, die über Chats hinweg bleiben: wer der User ist, Entscheidungen, Eigenheiten der Rechner – im Repo versioniert.
Entscheidungen müssen nicht in jedem Chat neu erklärt werden.
Claim
Zeile „Chat X bearbeitet Datei Y“ in TODOS.md; per Git für alle Chats und Rechner sichtbar – verhindert doppelte Arbeit.
Zwei Chats ändern nie gleichzeitig dieselbe Datei.
Lagebild
Übersicht beim Chat-Start: laufende Chats, Claims, offene Übergaben, fällige Team-Rituale.
Vor dem Start wissen, was schon läuft – keine doppelte Arbeit, nichts bleibt liegen.
Übergabe
Starttext für einen neuen Chat („chat weiter …“), wenn Kontext oder Aufgabe zu groß werden.
Ein frischer Chat macht nahtlos weiter, ohne Wissen zu verlieren.
Prüfstufe
Wie tief eine Änderung vor „fertig“ geprüft wird: 0 trivial bis 3 kritisch; im Zweifel eine Stufe höher.
Aufwand passt zur Änderung: Kleines schnell, Kritisches gründlich.
Vorschau
Webseite mit Varianten einer geplanten Änderung; der User wählt dort, erst dann entsteht Code.
Der User entscheidet, bevor Aufwand in Code fließt.
Pull · Push
Stand aus dem Repo holen · eigenen Stand hochladen; ein Push löst Prüfung und Bau dieser Seite aus.
Alle Rechner und Chats bleiben auf demselben Stand.
