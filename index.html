Workflow-Seite öffnen

Der Ablauf im Detail – wer macht was

Drei Ansichten desselben Ablaufs – oben umschalten. Farbe = Gruppe, rot = hier hält der Chat an. Alle Einzelheiten stehen in der Tabelle darunter.

Alle Einzelheiten als Tabelle

Eine Zeile je Schritt · Spalten = wer handelt · letzte Spalte = wann der Chat anhält. Hooks sind Skripte, die von selbst laufen; die Spalte Git zeigt, was in den Repos ankommt.

SchrittDuChat · RolleSkills · AgentenHooks · laufen von selbstGitStopp, wenn …
1Auftrag Aufgabe in den Chat schreiben – Text, Bild oder Link. Mehrere Chats laufen parallel, jeder mit eigener ID. Rolle: Organizerliest Lagebild, Regeln und Memory Skill answer-page – festes Antwortformat, einmal je Chat geladen
  • session_overview.pyLagebild: parallele Chats, Claims, offene Übergaben
  • CLAUDE.mdRegeln + Memory-Index sind schon geladen
 Stand aller Repos vorher per ws_sync.sh geholt Freigaben gibt nur der User in diesem Chat – nie andere Chats, Agenten oder Webseiten
2Plan Rückfragen beantworten, Vorschau abnehmen Rolle: Organizerschätzt den Aufwand, wählt Fachrolle und Prüfstufe, plant Dateien und Vorgehen Finder-Tabelle → Skill zum Thema, z. B. preview, ui-change · Agent ws-explorer für breite Suche
  • chat_length_hint.pyerinnert an passende Skills, ab ~100k Token an einen neuen Chat
 – Unklar → Rückfrage per Dialog statt raten · neue UI-Elemente erst als Vorschau mit Varianten, dann Code
3Umsetzung – Rolle: Designer, Entwickler oder Redakteurdie in Schritt 2 gewählte Fachrolle – kleinster Diff am richtigen Ort; erst prüfen, ob es das im Repo schon gibt Skill zum Thema, bei Bugs root-cause · Agent ws-worker für klar umrissene Änderungen, der Haupt-Chat prüft den Diff
  • todo_claim_hook.pylegt einen Claim als Git-Ref an und trägt jede Datei vor dem Ändern ein
  • pre_tool_guard.pyprüft jeden Befehl vor dem Start
  • post_edit_check.pyprüft jede Datei direkt nach dem Speichern
 Claim sofort gepusht – andere Chats und Rechner sehen ihn Datei eines anderen Chats → erst abstimmen, nie überschreiben
4Prüfung – Rolle: PrüferDefinition of Done nach Prüfstufe 0–3; Beleg aus diesem Chat nach der letzten Änderung, kein „sollte gehen“ Skill test-isolated · Agenten test-runner, ui-verifier; kritischer Code: safety-reviewer
  • tools/pre-commitTests, Begriffe und Format vor jedem Commit
 Nur geprüfte Stände werden committet Prüfung rot → zurück zu Schritt 3, kein „fertig“
5Abschluss Ergebnis lesen: Ergebnis-Zeile, Prüf-Tabelle, Status Rolle: SynchronizerCommit + Push; Antwort im festen Format; offener Rest → Übergabe für einen neuen Chat Skill commit – Commit im Stil des Repos, nie --force
  • format_check.pyprüft das Antwortformat
  • chat_handoff.pyschreibt die Übergabe, löscht den Claim
 Commit + Push ins Repo des Projekts Nie git push --force, nie fremde Änderungen mitcommitten
6Verteilung Seite und Projekte nutzen – Git-Hooks arbeiten allein –
  • pre-push → pages_hook.shbaut lu4k87.github.io aus dem gepushten Stand
  • chat_sync.pysichert die Chat-Verläufe
  • post-mergehält den Checkout der Seite aktuell
 Andere Rechner holen den Stand per ws_sync.sh Repos bleiben privat, wenn nicht ausdrücklich öffentlich
  • Stopp = Chat hält an und fragt nach oder geht einen Schritt zurück
  • Nach Schritt 6 beginnt die nächste Aufgabe wieder bei 1

Rollen im Chat

Jede Aufgabe läuft durch vier Rollen – der Staffelstab zeigt, wer gerade dran ist. Rolle anklicken = dorthin springen.

1 / 4
  1. 1Organizer

    Start, Plan, Rückfragen, Aufteilen in Chats – jeder Chat beginnt hier

  2. 2Fachrolle

    Umsetzung – eine Fachrolle je Aufgabe, gewählt im Plan

    • Designer
    • Entwickler
    • Redakteur
    • Projektmanager
    • Scrum Master
    • Forscher
    • Marketing
    • 3D-Designer
  3. 3Prüfer

    Definition of Done vor „fertig“ – Beleg aus diesem Chat

  4. 4Synchronizer

    Commit + Push, parallele Chats abstimmen, Rest übergeben
