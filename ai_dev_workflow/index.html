01Aufbau

Sechs Schichten, ein Regelwerk

6Schichten
Prinzip

Ein Editor, ein Regelwerk, klare Rollen

Du entscheidest, der Chat setzt um. Regeln, Wissen und Prüfungen liegen als Dateien in Git: Jeder Chat startet mit denselben Vorgaben – auf jedem Rechner, in jedem Werkzeug.

Mensch

User

  • Nennt das Ziel – ein Satz reicht
  • Entscheidet bei Rückfragen und Varianten
  • Gibt riskante Schritte frei, z. B. Robot | Hardware
  • Nimmt das Ergebnis ab: Diff, Vorschau, Prüfausgabe
Assistenz

Chat

  • Plant vor dem ersten Edit, fragt bei echten Entscheidungen
  • Baut den kleinsten Diff am richtigen Ort
  • Belegt das Ergebnis mit Tests, zieht Doku nach, pusht
  • Lädt Skills und Agenten nur, wenn die Aufgabe sie braucht
Gedächtnis

Zwei Repos

  • Werkzeug-Repo: Regeln, Skills, Hooks, Agenten für alle Projekte
  • Projekt-Repo: Code, Doku, eigene Regeln in AGENTS.md
  • Prüfskripte in bin/, tools/ und in den Skills
  • Git hält Laptop, Labor- und Home-PC gleich
  • VS CodeChat neben dem Code
  • RegelnRULES.md + AGENTS.md für jeden Chat
  • SkillsFachwissen, nur bei Bedarf geladen
  • AgentenSuchen und prüfen, ohne den Chat zu füllen
  • HooksPrüfen jeden Schritt automatisch
  • MemoryKorrekturen bleiben erhalten
  • GitJeder Stand gesichert
1.1Überblick

Wer macht was

Unter allen drei Werkzeugen liegen dieselben sechs Schichten – deshalb befolgt jeder Chat dieselben Regeln. Das Schema darunter zeigt, wer Ziele setzt, wer arbeitet, wer prüft und wo das Ergebnis landet.

Sechs Schichten liegen unter allen drei KI-Werkzeugen; Git hält sie auf jedem Rechner gleich.

1.2Arbeitsplatz

Am Beispiel Claude Code in VS Code teilen sich Code, Terminal, Git und Chat ein Fenster; du siehst jeden Schritt, jede Änderung und jeden Befehl. Einzelne Funktionen unterscheiden sich in Codex und Gemini / Antigravity.

Opus für Roboter, Sicherheit und Entscheidungen; Sonnet für leichte, prüfbare Aufgaben. So kostet Routine weniger, ohne dass die Qualität leidet.

Ein Arbeitstag

Vom Öffnen bis zum letzten Push – jeden Tag dieselben fünf Schritte.

  1. Öffnen, abgleichen

    tools/ws_sync.sh holt die Commits der anderen Rechner, baut geänderte Pakete und gleicht Settings ab.

  2. Ein Chat je Aufgabe

    Du nennst das Ziel, nicht den Lösungsweg. Das Lagebild beim Start zeigt, welche Dateien andere Chats gerade ändern.

  3. Parallel arbeiten

    Ein zweiter Tab übernimmt ein anderes Thema. Das Datei-Register warnt, bevor ein Chat fremde Änderungen überschreibt.

  4. Entscheiden, abnehmen

    Du beantwortest Rückfragen im Dialog, wählst Varianten in der Vorschau und prüfst Änderungen im Diff.

  5. Am Ende gepusht

    Jede fertige Aufgabe ist committet und gepusht – der nächste Rechner startet mit demselben Stand.

2.1Kreislauf

Zehn Schritte von der Anfrage bis zur Antwort

Jede Anfrage nutzt nur die Schritte, die sie braucht: Eine reine Frage überspringt Planen, Bauen und Prüfen, eine neue UI-Funktion durchläuft alle zehn. Wähle unten einen Weg – der Ring zeigt, welche Schritte er nutzt.

Fünf Phasen mit je einem Zuständigen; ein roter Test schickt den Auftrag zurück ins Bauen. Die zehn Schritte darunter verteilen sich so: Beauftragen 01 · Planen 02–05 · Bauen 06 · Prüfen 07–08 · Abliefern 09–10.

Weg
01

Anfrage

übersprungen

Du beschreibst das Ziel, nicht den Lösungsweg – Code und Regeln kennt der Chat selbst. Beim Start legt der Hook session_overview.py ein Lagebild bei: welche Dateien andere Chats gerade ändern.

Präfix [RCU] · [VLA] · [Doku]session_overview.pychat_length_hint.py
02

Aufwand zuerst prüfen

übersprungen

Bevor etwas geladen wird, klärt der Chat: Was braucht diese Anfrage wirklich? Jeder Skill und jeder Test kostet Zeit und Token – eine reine Frage bekommt deshalb eine kurze Antwort ohne beides.

  • Skills nur, wenn die Anfrage ihr Thema berührt – einmal je Chat
  • Subagenten nur, wenn eine breite Suche sonst teurer wäre
  • Nie gekürzt: Sicherheit (§0) und Antwortformat
03

Kontext laden

übersprungen

AGENTS.md und das Memory liegen jedem Chat bei, dazu die passenden Skills und das CLAUDE.md des Pakets. Große Dateien liest der Chat nie ganz, sondern sucht erst mit grep -n – das hält den Kontext klein.

AGENTS.mdMEMORY.mdsrc/<pkg>/CLAUDE.mdreferences/*.txt
04

Planen und nachfragen

übersprungen

Vor jeder größeren Änderung steht ein kurzer Plan: betroffene Dateien, Vorgehen. Echte Entscheidungen fragt der Chat, statt zu raten – als nummerierte Frage ❓ F1 und als Dialog zum Anklicken.

  • Deine Auswahl ist die Antwort – der Chat arbeitet direkt weiter
  • Unabhängige Teile: Der Chat schlägt einen neuen Chat mit fertigem Starttext vor
05

Vorschau-Seite

übersprungen

Bei neuen UI-Elementen und größeren Umbauten gilt: erst sehen, dann bauen. Die Vorschau-Seite zeigt jede Variante mit echtem Screenshot, jede Einzeländerung und jede Frage mit eigenem Bild, dazu je Variante den Button „Diese Variante wählen“; du entscheidest dort, bevor Code entsteht – das spart Umbauten im Code.

spec.jsoncapture.pybuild.py --look
06

Umsetzen – schlank statt überbaut

übersprungen

Vor jedem Code prüft die Ponytail-Leiter der Reihe nach: nötig, schon im Repo, Stdlib, Plattform nativ. Erst dann entsteht das Minimum, das funktioniert – weniger Code heißt weniger Fehler.

  • Bugfix = Ursache finden: alle Aufrufer greppen, gemeinsame Funktion einmal fixen
  • Nie gespart: Sicherheit, Eingabeprüfung, Schutz vor Datenverlust, Barrierefreiheit
  • Jeder Edit läuft durch zwei Hooks: einen davor, einen danach
07

Prüfen mit Beleg

übersprungen

„Fertig“ meldet der Chat nur mit Prüfausgabe nach der letzten Änderung, nie mit „sollte gehen“. Die Prüfstufe 0–3 legt die Tiefe fest; Tests laufen isoliert (eigene Domain, eigener Port), damit laufende Stacks ungestört bleiben.

tools/pre-commit --changedui_new_code_checker.pygrasp_e2e.py --quicksafety-reviewer
08

Doku wird mitgeschrieben

übersprungen

Bei neuer Funktion, neuem Namen oder Port ändert der Chat docs/en + docs/de, README, Handbuch und Setup-Karte im selben Zug, damit Doku und Code gemeinsam aktuell bleiben. check_showcase.py prüft Namen und Links.

09

Commit + Push

übersprungen

Nach jeder fertigen Aufgabe committet und pusht der Chat ohne Nachfrage – so ist jeder Stand gesichert und auf allen Rechnern abrufbar. Nur fertige, geprüfte, eigene Stände; Dateien anderer Chats bleiben draußen, nie --force.

10

Antwort in fester Form

übersprungen

Die erste Zeile nennt das Ergebnis mit Belegen, darunter nur Abweichungen und Details als Stichpunkte. Am Schluss stehen immer Zustand und Git-Stand: erledigt oder worauf der Chat wartet, dazu Chat-ID und ob gepusht ist. Lief ein MCP-Server oder Subagent, nennt eine Tabelle Werkzeug, Herkunft und Ergebnis. Rückfragen stehen ganz unten. Der Stop-Hook format_check.py blockt falsche Angaben, z. B. einen Push-Hash ohne Commit.

Kurzform

  1. Enter
  2. Pull + Claim
  3. Planen + Skills
  4. [Prüfen → Werkzeug → Prüfen] × n
  5. Prüfen + Push
  6. format_check
  7. Antwort

03Leitplanken

Sechs Prüfstellen, klare Grenzen

6Prüfstellen
3.1Leitplanken

Hooks im Takt eines Chats

Eine Regel, die nur im Text steht, kann ein Chat übersehen. Hooks sind Skripte, die an sechs festen Stellen automatisch laufen: Sie geben Kontext, warnen, fragen nach oder blockieren – immer mit Grund.

Sechs Hooks vom Chat-Start bis zum Commit. Station 4 ist die eigentliche Arbeit; die Hooks davor und danach (3, 5) laufen bei jedem Edit erneut.

1234567
1 · SessionStart

session_overview.py

Zeigt beim Start, welche Dateien andere Chats uncommittet geändert haben – so überschreibt kein Chat fremde Arbeit. Gemini bekommt Chat-ID, Übergaben und Postfach über agy_hook.py, vor jedem Modellaufruf zusätzlich Git-Stand und Postfach.

Kontext
2 · UserPromptSubmit

chat_length_hint.py

Meldet ab ~100k Token einen langen Kontext, ab ~160k deutlicher: Ein neuer Chat arbeitet dann schneller und günstiger. Codex nutzt dafür den Prompt-Adapter.

Hinweis
3 · PreToolUse

pre_tool_guard.py

Prüft jeden Befehl und Edit, bevor er läuft: breites pkill, echte robot_ip, geschützte und fremde Dateien. Riskantes braucht dein OK, sonst gibt es eine Warnung; Codex blockt harte Fälle mit deny.

Rückfrage · Warnung
4 · Werkzeug

Edit · Write · Bash

Die eigentliche Arbeit – Datei ändern, Test starten, Skript ausführen.

Arbeit
5 · PostToolUse

post_edit_check.py

Prüft jede geänderte Datei sofort: flake8, JSON/YAML, UI-Regeln (z. B. cursor: help, Akzent-Rand) und tools/check_*. Fehler fallen so beim Edit auf, nicht erst beim Commit.

Befund → sofort beheben
6 · Stop

format_check.py

Prüft jede Antwort auf falsche Angaben, z. B. „gepusht“ ohne Push oder eine Rückfrage außerhalb von „Jetzt du“. Formfehler meldet er nur als Hinweis; in Gemini lässt ein Wahrheitsfehler den Chat weiterarbeiten, Formhinweise kommen beim nächsten Aufruf über das Postfach.

Block → Schluss neu
7 · git commit

tools/pre-commit

Prüft nur die zum Commit vorgemerkten Dateien, meist unter 10 s; erinnert bei sicherheitskritischen Pfaden an den safety-reviewer.

Prüfung
3.2Rechte

Was der Chat ohne dich darf – und was nicht

Warum
Der Chat führt Befehle direkt im Workspace aus, und dieser Code bewegt echte Roboter-Hardware.

Weg eines Commits

Eigene Dateien sammeln

git status + Datei-Register: nur, was dieser Chat geändert hat.

tools/pre-commit

Prüft nur, was zu den vorgemerkten Pfaden passt: flake8, JSON/YAML, Ports, Showcase, Hook-Tests. Ist etwas rot, entsteht kein Commit.

Commit im Repo-Stil

Conventional Commits mit Bereich, z. B. fix(motion): … – der Verlauf zeigt so Art und Ort jeder Änderung.

Geprüften Stand pushen

Nur Fast-Forward: Der Push hängt Commits an und überschreibt nichts. Ist ein anderer Rechner voraus, holt tools/ws_sync.sh erst dessen Stand – aber nur, wenn gerade kein Chat ändert.

5.1Abstimmung

Acht Wege, sich abzustimmen

Mehrere Chats, Rechner und Werkzeuge arbeiten am selben Repo. Acht Wege sorgen dafür, dass jeder weiß, wer woran arbeitet – je nach Reichweite für einen Chat, einen Rechner oder alle Rechner.

Von innen nach außen: Was nur im Chat gilt (6, 7), was alle Chats eines Rechners sehen (1, 2) und was über Git alle Rechner erreicht (3, 4, 5, 8).

  1. Datei-Register + Lagebild Jeder Chat trägt geänderte Dateien live in ein Register in /tmp ein – je Git-Repo, Claude, Codex und Gemini (globaler Hook, file_register.py). Beim Start zeigt session_overview.py daraus, welche Dateien anderen Chats gehören.
  2. SendMessage + Teambesprechung Laufende Chats auf demselben Rechner schreiben sich direkt per SendMessage; die Teambesprechung ist eine Runde an alle laufenden Chats.
  3. Claims in TODOS.md Jede Aufgabe mit Dateiänderung erhält beim ersten Edit eine Zeile „🔒 In Arbeit“ in TODOS.md; ein sofortiger Push macht sie für andere Rechner sichtbar.
  4. Übergabe Soll ein neuer Chat weitermachen, steht Aufgabe und Kontext in .claude/handoff/*.md. Der neue Chat startet mit „chat weiter <kennung>“ und übernimmt sie.
  5. Memory, Regeln, Skills Wissen liegt als Dateien in Git (Werkzeug-Repo + Projekt-Repo): Memory (Erkenntnisse), Regeln (AGENTS.md, RULES.md) und Skills. Claude, Codex und Gemini lesen dieselben Dateien.
  6. Kontext des Chats Geladene Skills, Annahmen und Plan liegen nur im Kontext dieses Chats und enden mit ihm. Was bleiben soll, gehört deshalb in Memory, Regeln oder eine Übergabe.
  7. Scratchpad Einmal-Skripte und Zwischenergebnisse kommen ins Scratchpad des Chats, nie ins Repo – so bleibt das Repo frei von Wegwerf-Dateien.
  8. Abgleich der Rechner tools/ws_sync.sh holt den Git-Stand auf jedem Rechner und ruft den globalen Abgleich auf; chat_sync.py überträgt die Chat-Verläufe.

5.2Konflikte

Vier Arten von Konflikten, vier Reaktionen

Ein Konflikt entsteht, wenn zwei Chats, du oder zwei Rechner dieselbe Datei ändern, ohne sich abzustimmen. Der Workflow erkennt vier Arten – je früher er einen Konflikt erkennt, desto weniger Arbeit geht verloren.

Claim-Konflikt

Vor dem Edit

Auslöser
Die Datei steht im Claim eines anderen Chats (eigener Git-Ref je Chat, auch von anderen Rechnern).

Dann
Nicht ändern, mit dem anderen Chat abstimmen (SendMessage). Codex blockiert den Edit (deny).

Datei-Konflikt

Beim Edit

Auslöser
Die Datei hat uncommittete Änderungen eines anderen Chats oder einer unbekannten Quelle.

Dann
Das Datei-Register (globaler Hook, jedes Git-Repo, Claude, Codex und Gemini) warnt einmal je Datei; danach mit dem anderen Chat abstimmen. Müssen beide dieselbe Datei ändern: im Scratchpad vorbereiten, per 3-Wege-Merge zusammenführen.

Index-Konflikt

Beim Commit

Auslöser
Ein Commit würde fremde Änderungen aus dem gemeinsamen Index oder Arbeitsbaum mitnehmen.

Dann
Der Hook warnt bei git add/commit (Gemini: Rückfrage). Nur eigene Dateien stagen; bei geteilten Dateien privaten Index nutzen, vor dem Push git show --stat HEAD prüfen.

Git-Konflikt

Beim Sync

Auslöser
push abgelehnt oder kein Fast-Forward möglich; ws_sync.sh rebased nie über uncommittete Dateien anderer Chats.

Dann
Zuerst tools/ws_sync.sh; listet es fremde Dateien, mit deren Chats abstimmen und committen, dann erneut; nie --force.

6.1Gedächtnis

Wiederkehrende Korrekturen werden Regeln

Der Kontext eines Chats endet, das Repo bleibt. Dauerhafte Präferenzen und wiederkehrende Korrekturen werden in Memory, AGENTS.md oder einem Skill festgehalten und oft durch einen Hook abgesichert. Alle 4 Tage stellt der Chat zwei bis drei gezielte Fragen zum Workflow und setzt die Antworten um.

Sechs Stationen von einer wiederkehrenden Korrektur oder dauerhaften Präferenz bis zur Regel, die jeder Chat befolgt; der Workflow-Check sammelt Belege für die nächste Verbesserung.

  • Wiederkehrende Korrektur Du wiederholst eine Korrektur oder nennst eine dauerhafte Präferenz, z. B. „Ecken dezent runden“.
  • Festhalten Der Chat legt eine Memory-Datei an (eine je Erkenntnis, mit Grund) oder ergänzt AGENTS.md bzw. einen Skill.
  • Durchsetzen Wo möglich wird aus der Regel ein Hook, Prüfskript oder Test; neue Zeilen werden dann automatisch geprüft.
  • Verteilen Git, ws_sync.sh und agents_sync.py bringen die Regel auf alle Rechner und in alle drei Werkzeuge.
  • Jeder Chat befolgt sie Regeln stehen im Kontext, Hooks prüfen mit.
  • Belege sammeln Der Agent teamwork-optimizer sammelt Belege für den Workflow-Check (alle 3 Tage); das Team-Briefing folgt alle 7 Tage – daraus entsteht die nächste Korrektur.
