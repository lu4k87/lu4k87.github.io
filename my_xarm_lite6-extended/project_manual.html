UX-Regeln im Code
Sicherheit

Sicherheit liegt nicht im Browser

  • Remote-Gamepad: WLAN weg oder Tab verdeckt → kein Heartbeat → Watchdog stoppt selbst
  • Kollisionsvorprüfung, Servo und Not-Aus laufen auf dem Server
Sicherheit

Wer steuert, ist eindeutig

  • Zuschauen: beliebig viele Geräte · Bewegen: nur der Inhaber des Control-Locks
  • Prüfung Remote-Gamepad: Server · UI-Buttons, Jog, VR: Browser (motionAllowed)
  • REAL: Remote-Gamepad braucht zusätzlich eine Freigabe
Bewegung

Planen vor Ausführen

  • Zielpose wird erst geplant und als Pfad gezeigt
  • Fahren erst nach Bestätigung (/ui/confirm_moveto_preview)
Zustand

Ein Zustand, viele Ansichten

  • VR-Handgelenk-Panel spiegelt die DOM-Buttons der Desktop-Seite
  • Logik existiert nur einmal
Layout

Layout gehört dem Nutzer

  • Sektionen zwischen Spalten ziehen
  • HUD-Tabs andocken, Presets speichern
  • Nichts überlappt, nichts wird gequetscht
Rückmeldung

Fehler enden sichtbar

  • Stream ohne Kamera: 5 Versuche mit wachsendem Abstand
  • Danach „Try again“ statt stillem Weiterlaufen

Server · Roboter-PC
  1. Firewall öffnen
    • ufw ist aktiv, ohne Freigabe laden Clients nichts
    • Empfohlen: Skript erlaubt Heimnetz + Roboter-, Tobii- und Kamera-Netze aus config/network.yaml (je /24), sperrt alle anderen
    • Anderes Netz (z. B. Uni-WLAN): erneut --apply · weiteres Netz: --net <CIDR>
    cd ~/dev_ws && tools/firewall_setup.sh   # zeigt nur die Regeln
tools/firewall_setup.sh --apply           # setzt sie (sudo)
    • Oder nur die Ports freigeben · 8443 und 9091 nur für HTTPS (C, D)
    sudo ufw allow from 192.168.0.0/24 to any port 8081,8082,9090,8443,9091 proto tcp
sudo ufw status
    • Nur für F (zweiter PC mit ROS), wenn nicht per Skript: DDS läuft über UDP, auf beiden PCs freigeben
    sudo ufw allow from 192.168.0.0/24 proto udp
  2. Pakete bauen
    • Nur nach Änderungen an Watchdog oder Launch
    • Stand: gebaut
    cd ~/dev_ws && colcon build --packages-select remote_control_watchdog http_robot_control_ui_p8081
source install/setup.bash

    • Remote access an
    • Allowed clients: subnet
    • Details: Nexus-Werte

    • Erzeugt der erste Start von „VR Quest 3 Teleop“ (certs/cert.pem, aktuelle IP)
    • Neue IP → beim nächsten Start neu erzeugt
  5. Feste IP im Router
    • IP kommt per DHCP
    • Neue IP → Lesezeichen ungültig
    • Aktuelle URLs: Remote-Panel (8)

  • YOLO-Erkennungen und virtuelle Objekte kommen im selben Format

Virtuelle Objekte greifen

nur FAKE
  • Planning → Simulation → SIM physics an: Cube, Rectangle, Cylinder und die Grasp-Items werden echte Körper
  • Agent: Saugen an + Saugnapf auf der Oberseite → Objekt hängt am Greifer; die Sandbox meldet das gehaltene Objekt zurück (Greifprüfung)
  • Loslassen → Objekt fällt, Position geht zurück in die TF-Frames
  • Sandbox aus: der Arm fährt, die Objekte bleiben stehen (Hinweis im Chat, Ergebnis „Done - arm only“)
  • Umgekippte Objekte (Greiffläche > 20° schräg) greift der Agent nicht - erst aufstellen (TF Tuner / Reset der Physik-Objekte)
  • REAL-Roboter: Virtual darf an bleiben - virtuelle Objekte sind dann nur Hindernisse für MoveIt; Grasp / Place here darauf gesperrt, Move to mit zweitem Klick
  • Detected Objects: Kacheln Camera (real) (Live + Rate / nicht gestartet) und Virtual (Schalter), Zeilen mit Badge CAMERA / VIRTUAL

Regeln im Node

  • Neue Anweisung während THINKING/RUNNING → busy, wird abgelehnt
  • Neue Anweisung, während ein Plan wartet → ersetzt den Plan
  • Execute zählt nur mit passender id
  • Plan wird vor jeder Bewegung geprüft; Fehler gehen ans Modell zurück (max. 2 Korrekturen)
  • REAL ohne allow_real_motion → preview (nur Plan) · virtuelle Objekte nie · jeder Plan wartet auf Execute
  • Not-Aus aktiv → nichts wird ausgeführt
  • Fehler eines Schritts → replan: der Agent sieht Fehler und neue Szene und plant neu (max. 2×), sonst error mit Schritt und Grund
