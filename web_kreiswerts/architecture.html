01The big picture

Four layers, top to bottom. The browser only talks to the Next.js app; the app only reaches data through the server logic in src/server/.

✕

The browser never touches the database. Data goes through /api/* or a DAL function.

✓

The backend decides visibility. If a field is missing in the response, that role may not see it – hiding it in the UI is no protection.

✓

One schema, two jobs. A Zod schema validates the input and gives the TypeScript type for frontend and backend.

Each software part: what it does, where it lives, its functions and the rules it enforces. Colours match the colour key at the top.

Node.js

runtime · runs the server

The JavaScript runtime on the server. One Node.js process runs Next.js – pages, route handlers, Better Auth, Zod, the DAL and Drizzle with its database pool. The browser never runs this code.

Files

  • package.json
  • .nvmrc
  • .env
  • node_modules/

Functions

npm run dev
Development server with hot reload on http://localhost:3000
npm run build · npm start
Production build, then the production server
npm run check
TypeScript check + Vitest tests – must pass before every commit
npm run db:* · auth:schema
Database commands (drizzle-kit) and Better Auth schema generator
.env
Read at start: DATABASE_URL, BETTER_AUTH_SECRET, BETTER_AUTH_URL

Good to know

  • Version: Node.js ≥ 20.9 (.nvmrc: 20); Node 24 works too.
  • pg is loaded by Node at runtime, not bundled (serverExternalPackages).
  • Modules marked server-only can only run here – never in the browser.
  • Vitest stays on 4.x: version 5 breaks npm install with npm 10.

Next.js app

One Next.js 16 project (App Router) serves pages and the API. Every URL is a folder in src/app/.

Files

  • next.config.ts

Functions

Better Auth

station 2 · who is asking?

Login library: creates accounts, checks passwords, sets the session cookie and keeps its data in its own auth_* tables.

Files

  • src/server/auth.ts
  • src/server/viewer.ts
  • src/lib/auth-client.ts
  • src/lib/auth-errors.ts

Functions

auth
Config: email + password, username plugin, Drizzle adapter, Next.js cookies
getViewer(headers)
Guest → { role: "guest" }
Member → { role: "member", userId, siteId }
authClient.*
Browser: signUp.email, signIn.email, signIn.username, signOut
authErrorText(error, locale)
Error code → readable sentence in German or English

Good to know

  • Extra user fields: companyName, vatId, materialInterest (checked by Zod) and siteId (set by the backend only).
  • Hook before sign-up and password change runs registrationError() → 400 with a code.
  • Username 3–30 characters (a–z, 0–9, _ .); login attempts are rate-limited.

Zod validation

station 3 · is the input valid?

Checks every input before it reaches the database. One schema gives both the check and the TypeScript type.

Files

  • src/server/validation/offers.ts
  • src/server/validation/registration.ts

Functions

offerListQuery
materialId positive integer · city 1–100 characters · limit 1–100 (default 50) · empty = ignored
registrationError(body)
First invalid field as an error code, otherwise null
vatIdSchema
EU VAT ID; spaces, dots, dashes are removed:
DE 294 681 207 → DE294681207
passwordSchema
8–128 characters with at least one digit and one capital letter

Good to know

  • Company name 2–200 characters; material interest is one of 8 fixed values; a username is required (3–30 characters).
  • Codes: INVALID_COMPANY_NAME, INVALID_VAT_ID, INVALID_MATERIAL_INTEREST, INVALID_USERNAME, PASSWORD_TOO_WEAK.
  • The browser checks the same rules for quick feedback – the server check is the one that counts.

04One request, five stations

The reference example is src/app/api/offers/route.ts – all five stations in 15 lines. Every new endpoint follows the same order.

Guest · no cookie

Sees what an offer is and where.

  • title
  • materialName
  • availableQuantityKg
  • city

Member · session cookie

Sees everything a guest sees, plus price and contact.

  • title
  • materialName
  • availableQuantityKg
  • city
  • priceEurPerKg
  • description
  • contactName
  • contactEmail
  • contactPhone

05Getting data into a page

Rule of thumb: reading (lists, details) → server component. Interactive (form, map, live filter) → a small client component that calls the API.

A · Server component (default)

page.tsx→getViewer()→DAL function→DB

Rendered on the server: no loading state, the login cookie is read automatically. Filters come from the URL.

// src/app/page.tsx
const [viewer, stats] = await Promise.all([
  getViewer(await headers()),
  getPlatformStats(),
]);

B · Client component

"use client"→fetch /api/…→route→DAL

For interactive parts. Login and sign-up use authClient, which calls /api/auth/*.

"use client";
const res = await fetch(
  "/api/offers?city=Moers");
const { role, offers } =
  await res.json();

✕ Never

Import @/server/db/* in a page or component. It skips login, validation and the access rules.

Server code inside a "use client" file fails the build – use fetch there.

11Adding a feature

  1. Plan it

    Row + short section in docs/FEATURES.md: what, data, logic, open points.

  2. Rules + data

    Has a status flow → add it to status.ts with a test. Needs tables → ask the DB owners.

  3. Define the response type

    Like GuestOffer / MemberOffer. The frontend can build with mock data of exactly that type.

  4. Build the five stations
    Route→Auth→Zod→DAL→Drizzle

    Then add the endpoint to docs/FRONTEND.md.
