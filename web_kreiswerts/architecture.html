How the platform works – and how to build on it

One Next.js project holds the pages and the API of the material marketplace: offers (Level 1), requests and explained matching (Level 2, part 1), negotiations and exchanges (Level 2, part 2). Every request walks the same five stations on the server before it touches the database. This page shows the layers, the features, the request path, the API, the server functions, the database and the tools – everything you need to add a page or a feature.

01The big picture

Four layers, top to bottom. The browser only talks to the Next.js app; the app only reaches data through the server logic in src/server/.

✕

The browser never touches the database. Data goes through /api/* or a DAL function.

✓

The backend decides visibility. If a field is missing in the response, that role may not see it – hiding it in the UI is no protection.

✓

One schema, two jobs. A Zod schema validates the input and gives the TypeScript type for frontend and backend.

  • role and siteId are set by the server only (input: false); an administrator exists only through the seed.

04One request, five stations

The reference example is src/app/api/offers/route.ts – all five stations in a few lines. Every endpoint follows the same order.

Guest · no cookie

Sees the public pages and the public projection only.

  • park areas
  • named sites
  • categories
  • simulated pathways

Site, pending or declined

Sees and edits what is its own. Publishing, searching and contacting wait for the verification.

  • own profile
  • own drafts
  • own offers

Site, verified

Publishes offers and requests, searches, contacts and responds to other sites.

  • offers
  • requests
  • matches
  • distance
  • map
  • directory
  • enquiries
  • responses
  • supplier contact, if shown

Administrator

Verifies sites and maintains reference data. Reads listings, never acts as a site.

  • verification
  • reference data
  • addresses of sites

05Getting data into a page

Rule of thumb: reading (lists, details) → server component. Interactive (form, map, live filter) → a small client component that calls the API.

A · Server component (default)

page.tsx→getViewer()→DAL function→DB

Rendered on the server: no loading state, the login cookie is read automatically. Filters come from the URL.

// src/app/(platform)/offers/page.tsx
const page = await platformPage("browse", "/offers");
if (page.blocked) return page.blocked;
const result = await searchOffers(page.viewer, query);

B · Client component

"use client"→fetch /api/…→route→DAL

For interactive parts (forms, buttons). Login and sign-up use authClient, which calls /api/auth/*.

"use client";
const result = await apiRequest(
  "POST", "/api/my/offers", body);
if (!result.ok) showProblems(
  result.error.fields);

✕ Never

Import @/server/db/* in a page or component. It skips login, validation and the access rules.

Server code inside a "use client" file fails the build – use fetch there.

08The database

Twenty-six platform tables – 16 of Level 1, 6 for the material requests and 4 for negotiations and exchanges of Level 2 – plus the tables Better Auth needs for login. A physical site (sites) is the centre: it belongs to a company and an industrial park, owns offers, sends and receives enquiries, publishes requests, negotiates and exchanges with other sites and has exactly one login. The material catalogue is data, so a new category needs no new table.

09Status flows

Status values and allowed changes live once in src/server/domain/status.ts. Database, API, tests and UI all use the same values; canTransition() checks every change.

10Explained matching: four results, no score

evaluateMatch() in src/server/domain/matching.ts compares one request with one offer, criterion by criterion. Each criterion is met, failed, unknown or needs processing; the checks below run in this order and the first that applies sets the result. Matches are not stored – an edit on either side changes the result at once.

✕

IncompatibleA hard requirement failed. Lists only count these pairs.

2

Processing requiredNothing failed, but a step is needed – sorting, grinding or regranulation; the steps are named.

3

ConditionalNothing failed, no step, but a criterion is unknown – e.g. weaker evidence or free text.

✓

Compatible on declared dataEvery hard requirement is met by what both sites declared.

H

Hard criteriaCategory, material type, form, origin, quantity, timing, evidence and sample, technical criteria marked required.

P

Preferences never change the resultRecurring supply, price ceiling and delivery are shown next to it.

?

Unknown is never failedMissing data or free text cannot prove a mismatch – people review it.
