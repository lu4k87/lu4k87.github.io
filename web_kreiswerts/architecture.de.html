01Das große Bild

Vier Schichten, von oben nach unten. Der Browser spricht nur mit der Next.js-App; die App kommt nur über die Server-Logik an Daten, in src/server/.

✕

Der Browser greift nie auf die Datenbank zu. Daten laufen über /api/* oder eine DAL-Funktion.

✓

Das Backend entscheidet, was sichtbar ist. Fehlt ein Feld in der Antwort, darf diese Rolle es nicht sehen – Ausblenden in der Oberfläche ist kein Schutz.

✓

Ein Schema, zwei Aufgaben. Ein Zod-Schema prüft die Eingabe und liefert den TypeScript-Typ für Frontend und Backend.

Node.js

Laufzeit · führt den Server aus

Die JavaScript-Laufzeit auf dem Server. Ein Node.js-Prozess führt Next.js aus – Seiten, Route-Handler, Better Auth, Zod, den DAL und Drizzle mit seinem Datenbank-Pool. Der Browser führt diesen Code nie aus.

Dateien

  • package.json
  • .nvmrc
  • .env
  • node_modules/

Funktionen

Produktions-Build, danach der Produktionsserver

Datenbank-Befehle (drizzle-kit) und Schema-Generator von Better Auth

Gut zu wissen

  • Vitest bleibt auf 4.x: Version 5 bricht npm install mit npm 10 ab.

Next.js-App

Station 1 · Einstiegspunkte

Ein Next.js-16-Projekt (App Router) liefert Seiten und API. Jede URL ist ein Ordner in src/app/.

Dateien

  • src/app/api/*/route.ts
  • next.config.ts

Funktionen

GET /api/offers
route.ts: getViewer → Zod → listOffers → JSON { role, offers }
GET /api/health
Prüft mit select 1 → { ok, db }, oder 503, wenn die Datenbank nicht erreichbar ist
/api/auth/[...all]
Gibt jeden Aufruf an /api/auth/* an Better Auth weiter (toNextJsHandler)
next.config.ts
pg bleibt außerhalb des Bundles; alte URLs /registrieren und /konto leiten weiter (308)

Gut zu wissen

  • Route-Handler bleiben schlank: kein SQL und kein Feldfilter – das ist Aufgabe des DAL.
  • Seiten, die die Session lesen, werden je Anfrage gerendert (dynamisch).

Better Auth

Station 2 · wer fragt?

Login-Bibliothek: legt Konten an, prüft Passwörter, setzt das Session-Cookie und speichert alles in eigenen auth_* Tabellen.

Dateien

  • src/server/auth.ts
  • src/server/viewer.ts
  • src/lib/auth-client.ts
  • src/lib/auth-errors.ts

Funktionen

auth
Konfiguration: E-Mail + Passwort, Username-Plugin, Drizzle-Adapter, Next.js-Cookies
getViewer(headers)
Gast → { role: "guest" }
Mitglied → { role: "member", userId, siteId }
authClient.*
Browser: signUp.email, signIn.email, signIn.username, signOut
authErrorText(error, locale)
Fehlercode → lesbarer Satz auf Deutsch oder Englisch

Gut zu wissen

  • Zusätzliche Nutzerfelder: companyName, vatId, materialInterest (von Zod geprüft) und siteId (setzt nur das Backend).
  • Ein Hook vor Registrierung und Passwortänderung ruft registrationError() auf → 400 mit Code.
  • Benutzername 3–30 Zeichen (a–z, 0–9, _ .); Login-Versuche sind begrenzt.

Zod-Prüfung

Station 3 · ist die Eingabe gültig?

Prüft jede Eingabe, bevor sie die Datenbank erreicht. Ein Schema liefert Prüfung und TypeScript-Typ zugleich.

Dateien

  • src/server/validation/offers.ts
  • src/server/validation/registration.ts

Funktionen

offerListQuery
materialId positive ganze Zahl · city 1–100 Zeichen · limit 1–100 (Standard 50) · leer = ignoriert

vatIdSchema
EU-USt-IdNr.; Leerzeichen, Punkte, Bindestriche werden entfernt:
DE 294 681 207 → DE294681207
passwordSchema
8–128 Zeichen mit mindestens einer Zahl und einem Großbuchstaben

Gut zu wissen

  • Firmenname 2–200 Zeichen; Material-Interesse ist einer von 8 festen Werten; ein Benutzername ist Pflicht (3–30 Zeichen).
  • Codes: INVALID_COMPANY_NAME, INVALID_VAT_ID, INVALID_MATERIAL_INTEREST, INVALID_USERNAME, PASSWORD_TOO_WEAK.
  • Der Browser prüft dieselben Regeln für schnelles Feedback – maßgeblich ist die Prüfung auf dem Server.

05Daten in eine Seite holen

Faustregel: Lesen (Listen, Details) → Server Component. Interaktiv (Formular, Karte, Live-Filter) → kleine Client-Komponente, die die API aufruft.

A · Server Component (Standard)

page.tsx→getViewer()→DAL-Funktion→DB

Auf dem Server gerendert: kein Ladezustand, das Login-Cookie wird automatisch gelesen. Filter kommen aus der URL.

// src/app/page.tsx
const [viewer, stats] = await Promise.all([
  getViewer(await headers()),
  getPlatformStats(),
]);

B · Client-Komponente

"use client"→fetch /api/…→route→DAL

Für interaktive Teile. Login und Registrierung nutzen authClient, der Anfragen schickt an /api/auth/*.

"use client";
const res = await fetch(
  "/api/offers?city=Moers");
const { role, offers } =
  await res.json();

✕ Nie

Import von @/server/db/* in einer Seite oder Komponente. Er umgeht Login, Prüfung und Zugriffsregeln.

Server-Code in einer "use client" Datei bricht den Build ab – dort fetch verwenden.

06API je Funktion

Alle Endpunkte – live und geplant – nach Funktion gruppiert: wer sie aufrufen darf, was hineingeht und was zurückkommt. Routen liegen in src/app/api/; Login-Routen kommen von Better Auth über /api/auth/[...all].

Basis

Gleiche Adresse wie die App (/api/…), JSON rein und raus.

Login

Das Session-Cookie geht auf derselben Seite automatisch mit – kein Token-Handling.

Fehler

400 { error, details } von Zod · 503 Datenbank nicht erreichbar · nur für Mitglieder → 401.

Rollen

Jede Antwort enthält role; fehlende Felder = für diese Rolle nicht erlaubt.

  • ⏳geplant
